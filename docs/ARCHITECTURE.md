# Устройство решения

## Данные

Продажи агрегируются суммой `quantity` по неделе, складу и товару; неделя начинается
в понедельник. Департаменты объединяются. Истории продаж и остатков соединяются
по складу, товару и временной метке после приведения к нужной гранулярности.

Повторяющиеся записи остатков одного товара на одном складе внутри дня суммируются.
По неделе рассчитываются последний остаток, средний остаток и доля дней
с неположительным остатком. Остатки разных дней не складываются как продажи.
Отрицательные остатки сохраняются. Будущие фактические остатки модели не доступны.

## Признаки

Актуальный список табличных признаков хранится в
[manifest.json](../forecast-container/model/manifest.json), всего 28:

- склад, товар, категории второго и третьего уровней;
- горизонт, индекс времени и календарные характеристики;
- лаги продаж 1/2/4/13, средние 4/13, стандартное отклонение и доля ненулевых продаж;
- продажи товара по сети, рост сетевого спроса, доля склада и активность складов;
- прошлые остатки, доля неположительных остатков, `unconstrained_demand_13`, `weeks_of_supply`.

`unconstrained_demand_13` — инженерная оценка, не наблюдаемый истинный спрос
при неограниченных запасах. Набор TFT отличается от табличного; он задан
сохранённой конфигурацией нейросети и подготовкой входа в predictor.
Категория первого уровня служит разделению моделей по категориям.

## Компоненты

| Компонент | Доля | Роль |
|---|---:|---|
| TFT | 45% | Прогноз временного ряда с дополнительными признаками |
| LightGBM | 37% | Вероятность продажи и оценка объёма; два регрессора L1/L2 |
| CatBoost | 9% | Табличный компонент ансамбля |
| LightGBM по категориям | 9% | Отдельные модели для групп товаров |

Для ряда компонентов применяются вероятностные пороги и собственная обработка.
После взвешенной суммы применяется множитель 1.05, порог 0.65, `np.rint` и
ограничение снизу нулём. Это настройки конкретного решения, не универсальный
способ оптимизации SMAPE. Источник параметров —
[postprocessing.json](../forecast-container/model/postprocessing.json).

## Инференс и сервис

`predict_from_history()` проверяет вход, строит признаки и вызывает сохранённые
модели. API принимает CSV, возвращает прогноз и кеширует последний результат.
Тесты включают повторный вызов с обходом кеша и изменение входных продаж:
это позволяет отличить реальное вычисление от возврата заготовленного CSV.

Для соревнования CLI фиксирует cutoff 2026-07-26; API вычисляет горизонт
относительно переданной истории. Проверка на полном наборе данных и запуск
на коротком демонстрационном срезе — разные сценарии.

## Foundation-модели

Chronos-2 и Timestral исследовались отдельно. Для Timestral проверены
предобученный прогноз, LoRA, дополнительные временные признаки и смешивание
с ансамблем. `predict_block()` возвращает исходную шкалу после внутреннего
обратного масштабирования; проверки сравнивали его с официальным inference.
Эти эксперименты не означают, что Timestral входит в сохранённый основной API.
