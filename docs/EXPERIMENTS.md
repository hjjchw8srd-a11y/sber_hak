# Карта исследований

Репозиторий хранит историю экспериментов. Следующие точки входа помогают
найти нужный этап без последовательного чтения всех скриптов.

| Этап | Точки входа | Что исследовалось |
|---|---|---|
| Подготовка | `prepare_weekly_data.py` | Недельная агрегация продаж и остатков |
| Признаки | `run_weekly_feature_experiments.py`, `info_about_sign.md` | История спроса, календарь, остатки, сеть |
| TFT | `train_tft_weekly.py`, `experiments/tft/` | Нейросетевой прогноз и обработка выхода |
| Ансамбль | `experiment_all_stock_ensemble.py`, `experiments/model_improvements/` | Бустинги, категории, признаки, смешивание |
| Сохранение ансамбля | `build_champion_bundle_and_submissions.py` | Обучение и экспорт; запуск изменяет артефакты |
| NHITS | `train_nhits_benchmark.py` | Альтернатива TFT, влияние функции потерь |
| Chronos | `run_chronos_small_benchmark.py`, `run_chronos_lora_fold4.py` | Zero-shot и адаптация |
| Timestral | `run_timestral_lora_fold.py`, `experiments/timestral_feature_research/` | LoRA, covariates, временные окна и seed |
| Доставка | `generate_submission_release.py`, `forecast-container/` | Воспроизведение, API и проверки |

## Как читать результаты

1. Начинайте с [актуальной сводки](RESULTS.md).
2. Сверяйте эксперимент с его JSON/CSV, датами отсечения и набором фолдов.
3. Не сравнивайте напрямую среднее двух окон со средним пяти окон.
4. Различайте исходный прогноз, округлённый прогноз и готовую смесь.
5. Старое название «champion» относится к моменту эксперимента и не является
   гарантией совпадения с текущим model bundle.

## Основные выводы

Редкий спрос делает SMAPE чувствительной к небольшим положительным прогнозам
на фактических нулях. Округление помогало в отдельных опытах, но одновременно
могло убирать настоящие небольшие продажи. RMSE, в свою очередь, сильнее
реагировала на крупные ошибки. Поэтому проверялись все пять метрик.

Предобученная модель без адаптации не обязательно лучше бустинга, обученного
на прикладных данных. Дообучение и дополнительные признаки помогали не во всех
периодах. Пользу нового компонента нужно проверять в смеси, а не выводить
из архитектуры модели или красивых отдельных примеров.

Проверки корректности выявляли проблемы именования контрольных моделей,
несопоставимые рецепты постобработки и расхождения отчётов с метриками.
Сохранение прогнозов по ключам и численные проверки оказались важной частью работы.

## Ограничения воспроизведения исследований

Полные исходные данные, часть OOF-прогнозов и большие pretrained-веса отсутствуют
в Git. Некоторые скрипты требуют локальных артефактов предыдущих этапов.
Не запускайте все `run_*.py` подряд: это история исследования, не единый build.
В README описан проверенный маршрут инференса основного ансамбля.
