## 4. Препроцессинг для произвольной даты и 180 дней

Начало прогноза: `max_date_sales.normalize() - Timedelta(days=max_date_sales.weekday()) + Timedelta(days=7)`. Ровно 9 понедельников. Для 2026-07-26 начало 2026-07-27; для пятницы 2026-07-31 начало 2026-08-03; для понедельника 2026-08-03 начало 2026-08-10.

Убрать из API фиксированные даты, origin=134 и обязательное число строк 79101. Для основного сабмита cutoff остаётся 2026-07-26; для API cutoff определяется запросом. Остатки после последней даты sales не должны попадать в признаки.

Переиспользовать проверенные правила подготовки данных:

- Продажи агрегировать по понедельнику недели × складу × артикулу с суммированием департаментов и остальных разрезов.
- Денежные значения преобразовывать как в обучении, до агрегации и ровно один раз. Для discount_sum сначала запомнить маску null: exp только для известных логарифмированных значений, исходный null превращается в денежный 0. Не делать exp(fillna(0)), иначе отсутствие скидки станет единицей. Валидатор не должен заранее уничтожать маску null.
- В stock переименовать char_article в article. Дубликаты одного дня и пары суммировать; остатки разных дней для недельного признака не суммировать. Недельные агрегаты и различие NaN/нуля сохранять как в обучении. Отрицательные остатки допустимы.
- Соединение продаж и остатков — после приведения ключей и агрегации. Проверить, что merge не размножает продажи.
- Нулевые продажи в пропущенные дни/недели добавлять только по принятому правилу для допустимых пар и внутри известного интервала наблюдений. Отсутствие истории до начала загрузки не выдавать за реальные нулевые продажи.
- Пары брать из явного справочника/эталонного перечня, а не молча из полного декартова произведения или только ненулевых продаж. Сохранить известные пары без продаж в загруженном окне. Политику неизвестных идентификаторов определить и описать; не подменять их первым известным ID и не терять молча.
- Сетевые агрегаты считать по всей входной сети до фильтрации GET.

Критичные места:

1. **time_idx.** Сейчас он зависит от позиции строки/первой недели входа. При загрузке последних 180 дней нельзя начинать время заново с 0. Сохранить календарный anchor обучения и вычислять совместимый абсолютный индекс для TFT и бустингов; позиционные индексы для массива лагов держать отдельно.
2. **Кодировки.** Переиспользовать обученные словари и порядок колонок. Не fit-ить encoder/scaler на запросе и не менять смысл кодов при отсутствии части товаров.
3. **Короткая история.** 180 дней не гарантируют 26 полных недель; TFT имеет input_size=26, а его ранние сетевые признаки требуют ещё прогрева rolling-окон. WeeklyMatrices также строит history26 даже для более коротких используемых признаков. Не допускать отрицательной индексации NumPy, чтения будущих строк или требования «пришлите год». Реализовать и документировать совместимую политику доступных окон/padding/mask; не притворяться, что недостающие наблюдения были известны. Если это меняет прогноз относительно полной истории, измерить отдельно.
4. **Неполные недели.** У API последняя неделя может заканчиваться в пятницу, а первая начинаться не в понедельник. Зафиксировать правило обработки, соответствующее смыслу входа; не молча масштабировать продажи до полной недели и не считать недостающие дни наблюдёнными нулями. Прогноз начинается именно со следующего понедельника по ТЗ.
5. **Будущие признаки.** Только известный календарь и исторические агрегаты. Не использовать фактические будущие продажи/остатки; технические строки будущего не должны попадать в rolling-историю. Не добавлять новые признаки ради API без обучения совместимой модели.

## 5. Реализовать HTTP-контракт раздела 10

Самодостаточная папка `forecast-container/`: Dockerfile, .dockerignore, зафиксированные зависимости, app/, model/ или механизм офлайн-подготовки bundle, tests/, README.md. Краткий README здесь требуется самим заданием со звёздочкой.

Загрузка моделей один раз при старте. Начать с одного worker; тяжёлые POST выполнять последовательно с явной блокировкой, чтобы не создавать несколько копий TFT в памяти. Ошибка запроса не должна повреждать последний успешный результат.

Эндпоинты:

- POST `/predict`: multipart-файлы `sales` и `stock`, построение реального прогноза, CSV `week,warehouse_name,article,quantity`.
- GET `/predict?article=...&warehouse=...`: хотя бы один параметр; без обоих 400. При двух — пересечение фильтров. Возвращать срез последнего успешного POST, не пересчитывать сетевые признаки на одном товаре.
- GET `/predict/all?format=csv|json`: полный последний прогноз; неизвестный format — 400.
- GET `/health`: готовность сервиса; не объявлять готовым, если обязательные модели не загрузились.

До первого POST возвращать понятную ошибку об отсутствии рассчитанного прогноза, например 409 с документированным code. Это выбранное поведение сервиса, а не дополнительное требование ТЗ. Не отдавать предзагруженный финальный submission. Кеш после успешного POST заменять атомарно; ключ кеша при использовании — содержимое обоих файлов и версия bundle, не только имена файлов.

Валидация:

- Пустые/нечитаемые CSV — 400.
- Обязательные колонки обоих файлов из раздела 2, строгие даты YYYY-MM-DD, корректные числовые значения и ключи.
- История каждого файла: `(max_date - min_date).days + 1 >= 180`; недостаточная — 422. Не требовать 180 дней для каждого отдельного товара. Проверять пригодность истории, фактически оставшейся после cutoff, и сообщать несогласованность файлов явно.
- Отрицательная quantity — 422; отрицательный stock разрешить.
- Null discount_sum разрешить с правилом выше; NaN/inf в выходном quantity запрещены.
- Все ошибки в едином формате `{"detail": "Описание", "code": "VALIDATION_ERROR"}`; для служебных состояний можно документировать отдельные code.

Для загрузки файлов FastAPI нужен python-multipart; использовать UploadFile, чтобы не держать лишние копии больших файлов. Официальная справка: https://fastapi.tiangolo.com/tutorial/request-files/.

## 6. Docker и реальные проверки

Образ должен содержать runtime-код, зависимости, модельные артефакты и статические преобразования. Не делать COPY всей рабочей папки: исключить датасеты, OOF, сабмиты, .git, .venv, локальные абсолютные пути и экспериментальные отчёты.

Зависимости проверить в чистом окружении: в текущем requirements нет явного LightGBM, а root/nested imports различаются. Сохранить реально проверенные совместимые версии, включая Torch/NeuralForecast, FastAPI/Uvicorn/python-multipart; добавить необходимые системные библиотеки LightGBM. Не менять версии ради «последних».

Инференс без внешней сети и без примонтированной папки проекта. Проверить в контейнере с отключённой сетью, выполняя HTTP smoke-test внутри контейнера, либо в изолированной внутренней сети без внешнего выхода. Не путать сетевой доступ к HTTP API с разрешением скачивать модель при запросе.

Обязательные проверки:

1. Чистый build, запуск, readiness, загрузка всех компонентов; реальный полный POST без моков.
2. Две одинаковые загрузки дают один отсортированный прогноз; проверить после перезапуска тоже. Записать hardware/seed/thread settings. Не обещать равенство между разным оборудованием без проверки.
3. GET-фильтры совпадают с соответствующими строками POST; CSV и JSON /all содержат одинаковые ключи и числа.
4. Ошибки: пустой файл, отсутствующая колонка, неправильная дата, quantity < 0, 179 дней. Ровно 180 дней принимаются; отрицательные остатки и null discount корректно обрабатываются.
5. Разные последние даты: воскресенье, пятница, понедельник; ровно 9 следующих понедельников. Прогноз не всегда возвращает июль 2026.
6. Уникальность и полнота допустимых пар × недель, finite quantity >= 0; stock-merge не умножает продажи. Перестановка входных строк не меняет результат.
7. Изменение продаж в тестовом входе проходит через признаки и raw-предсказания реальных моделей. Нельзя считать контракт проверенным только потому, что GET вернул заранее сохранённый CSV.
8. Сравнение полного CLI/API пути с кандидатом на всей разрешённой истории. Вывести расхождения отдельно по компонентам.
9. На одном существующем историческом фолде с моделями, обученными строго до cutoff, сравнить: полная доступная история vs последние 180 дней. Пять исходных метрик и локальный score, длительность, число строк, доля нулей. Не использовать для этого финальные модели, видевшие таргеты фолда. Этот фолд уже использовался в разработке: не называть его новым независимым тестом.
10. Измерить размер образа, время сборки, peak RAM, время POST/GET. Лимиты ТЗ: 30 GB образ, 64 GB RAM, 60 мин build и POST, 10 мин GET. Зафиксировать GPU/CPU режим. Если Docker недоступен, честно указать, что контейнерные проверки не выполнены; локальный TestClient их не заменяет.

Изменение входных остатков не обязано менять прогноз модели, у которой stock не входит в выбранные признаки. Не вводить фиктивную зависимость ради теста. В описании честно перечислить фактические признаки каждого компонента.

Если часть работы блокируется, заканчивай независимые части и укажи конкретный блокер. Не объявляй задание со звёздочкой выполненным до реального POST с моделью и Docker-проверки; качество контейнера «не хуже сабмита» отдельно подтвердить сравнением, а не обещанием.

Сейчас не добавлять Top-Down, новые признаки, Optuna и альтернативные модели: это отдельные эксперименты после готовности версии для защиты. Новые архитектурные изменения не должны смешиваться с упаковкой проверенного ансамбля.
