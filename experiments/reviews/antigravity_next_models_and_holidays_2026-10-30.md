### Как смешивать прогнозы без повторной обработки

`E_raw` — колонка `raw_blend` проверенного контроля B, до общей alpha и округления. В ней уже сохранена исходная компонентная обработка бустингов и категорийной модели; её в этом эксперименте не менять. `T_raw` — исходный прогноз TFT. `C_raw` — неотрицательный прогноз нового кандидата в единицах quantity (первый Chronos-вариант — медиана).

Общая функция финальной обработки:

```python
def P(x):
    z = 1.05 * np.maximum(np.asarray(x, dtype=float), 0.0)
    return np.maximum(np.rint(np.where(z < 0.65, 0.0, z)), 0.0)
```

На окнах выбора сравнить заранее заданные варианты:

```text
P(E_raw)                         # основной контроль
P(T_raw)                         # сопоставимый одиночный TFT
P(C_raw)                         # одиночный кандидат с тем же правилом
P(0.90 * E_raw + 0.10 * C_raw)
P(0.75 * E_raw + 0.25 * C_raw)
P(0.90 * T_raw + 0.10 * C_raw)
P(0.75 * T_raw + 0.25 * C_raw)
```

Дополнительно показать сырые прогнозы без P как диагностику. Не брать для `E_raw` колонки `scaled_blend` или `final_prediction`: иначе alpha/округление применятся повторно. Веса 10%/25% не оптимизировать отдельно по оцениваемому окну. Оставить вариант с весом кандидата 0, если улучшения нет. Это скрининг с фиксированной обработкой; неудача сама по себе не доказывает, что никакая другая обработка кандидата не поможет.

В эксперименте с праздниками заменить только компонент LightGBM: `E_holidays_raw = E_raw + 0.30 * (L_holidays - L_control)`, где обе L имеют одинаковую исходную компонентную обработку. Затем один раз применить P. Не добавлять новый LightGBM поверх уже включённых 30% и не менять остальные модели одновременно.

Сначала отчёт по folds 4, 3, 2 и записанный выбор; после этого без перенастройки — folds 1, 0. При сомнениях по памяти сначала smoke на фиксированных 100 рядах, результаты smoke не выдавать за качество на всей задаче. В первый этап не включать дообучение foundation-модели, stacking, подбор сегментных порогов и Optuna: это отдельные факторы для последующих проверок.

Минимальный результат этапа: `protocol.json`, `selected_config.json`, keyed-прогнозы, `metrics_by_fold.csv`, `REPORT.md`, журнал и точные команды повторения. Для каждого варианта показать пять исходных метрик, две локальные оценки, дельту относительно контроля, время и память. Отдельно указывать, выполнен запуск или только подготовлен код.

## 1. Проверить и локализовать общие ошибки

Предварительная независимая проверка уже выполнена на пяти сохранённых окнах. Источники: `experiments/history_window_audit/keyed_oof/blend_b_fold_{0..4}.csv.gz`, target из `experiments/stacking_honest/fold_meta_features/fold_{0..4}_meta.csv.gz`. Объединение строго по week/warehouse_name/article, one-to-one. На каждом окне 79101 строка. Ошибка = max(component_prediction, 0) - target. Использованы after_comp_tft и after_comp остальных моделей, до общей alpha/финального округления.

Средние по пяти окнам корреляции ошибок с TFT:

| Компонент | Все строки | Только target > 0 |
|---|---:|---:|
| LightGBM B | 0.8602 | 0.8540 |
| CatBoost | 0.8405 | 0.8326 |
| Категорийные модели | 0.8082 | 0.8005 |

Это поддерживает гипотезу о похожих ошибках, но не доказывает бесполезность ансамбля: текущая смесь уже выигрывает у TFT. Большие ошибки и масштаб рядов могут доминировать в Pearson correlation.

Создать воспроизводимый `analyze_model_complementarity.py` и отчёт `experiments/complementarity/`:

- Проверка уникальности, равенства наборов ключей, отсутствия NaN и совпадения target. Не заполнять отсутствующие предсказания нулями.
- Pearson ошибок на всех строках и положительных продажах; дополнительно ошибки, нормированные на исторический mean13 с явно заданной безопасной нижней границей. Сегменты задавать по истории до cutoff, не по будущим продажам.
- Сегменты: редкий/регулярный спрос, низкий/высокий исторический объём, рост/спад, horizon 1..9, категория. Раздельно ложные продажи на нуле, пропущенные продажи, большие недопрогнозы и большие перепрогнозы.
- Для каждой модели: пять исходных метрик, локальный capped score и uncapped diagnostic. Отдельно оценить добавление фиксированных 10% и 25% кандидата в TFT и в текущий ансамбль с одинаковой общей постобработкой.
- Показывать результат каждого окна, не только среднее. Не выбирать вес отдельно по таргетам оцениваемого окна. Oracle «выбрать лучший прогноз по факту» допустим только как помеченная недостижимая диагностика, не как стратегия или результат модели.
- Сохранить несколько графиков факт/прогноз: случайная воспроизводимая выборка рядов и отдельная подборка крупных ошибок, не выдавать подборку за репрезентативную.

## 2. Добавить календарь праздников отдельным блоком

В текущие 24 табличных признака и будущие входы TFT праздники не включены. Географическое допущение — федеральный календарь РФ; региональные даты без известного региона не придумывать.

Реализовать единый модуль календарных признаков для недель с понедельника по воскресенье:

- holiday_days: число федеральных праздничных дат внутри целевой недели;
- holiday_days_prev_week и holiday_days_next_week: события в соседних неделях;
- new_year_days и may_holiday_days: отдельные группы при проверке расширенного набора;
- дни до ближайшего праздника/после предыдущего с документированной точкой отсчёта и ограничением дальности;
- при наличии проверенного производственного календаря — число фактических нерабочих дней с переносами и рабочих суббот. Обычные выходные и официальные праздники различать. Постоянные «2 выходных в каждой полной неделе» отдельным полезным признаком не считать.

Праздники рассчитывать по датам прогнозируемых недель. Они известны заранее, поэтому их можно передавать в futr_exog TFT и остальных поддерживающих моделей. Переносы должны быть известны на дату исторического прогноза; учитывать публикацию календаря, не использовать будущую информацию о фактических продажах/акциях. Для statutory holidays достаточно проверенных правил, производственный календарь версионировать отдельно. Никакого скачивания календаря во время API-инференса.

Перечень федеральных праздников: https://mintrud.gov.ru/labour/relationship/351 и актуальная статья 112 ТК РФ: https://www.consultant.ru/document/cons_doc_LAW_34683/98ef2900507766e70ff29c0b9d8e2353ea80a1cf/ . Проверять переносы по соответствующим годам отдельно.

Важно: на целевом горизонте 2026-07-27..2026-09-21 федеральных праздничных дат нет. Не обещать, что этот блок сам решит проблему лидерборда. 1 сентября, сезон подготовки к учебному году, 11.11/Black Friday и промо — возможные коммерческие события, но не государственные нерабочие праздники. Если тестировать, создать отдельную группу признаков и не утверждать, что реальные акции известны.

Проверки календаря: январская неделя, неделя с 8 марта/9 мая/12 июня/4 ноября, переход года, високосный год, повторные и перемешанные даты, одинаковый результат на train и future. Состав будущих колонок должен точно совпадать с моделью. Старый checkpoint не принимает новые признаки автоматически: нужна отдельная обученная версия.

Абляция сначала на LightGBM B: текущий набор против текущего набора + праздничный блок, одинаковые 52 origins, 350000 sampled rows, seed, параметры и пороги. Если нет устойчивого выигрыша, не переносить в финал автоматически. Затем проверить TFT с праздниками, чтобы не отбирать нейросетевые признаки только по бустингу.

## 3. Первый новый нейросетевой кандидат — Chronos-2

Начать с pretrained `amazon/chronos-2` без дообучения. Это иной источник обучающих данных и другой способ построения прогноза, поэтому он интересен и как самостоятельная модель, и как дополнение к TFT. Выигрыш на наших данных не гарантирован.

Официальные источники:
- https://github.com/amazon-science/chronos-forecasting
- https://github.com/amazon-science/chronos-forecasting/blob/main/src/chronos/chronos2/pipeline.py
- https://arxiv.org/abs/2510.15821

Сначала небольшой smoke по памяти/скорости на фиксированных рядах, затем весь набор рядов на согласованных временных окнах. Проверить режимы: только история quantity; история + известный будущий календарь. Остатки и продажи сети можно подавать как past-only covariates, их будущее не подставлять из валидации. Дообучение и multivariate-группировку по товару/складам рассматривать только после zero-shot baseline.

Выходы median/доступные квантили сохранять отдельно; median не называть математическим ожиданием. Выбор квантиля/порога по SMAPE/WAPE делается только на окнах настройки. По умолчанию не вводить второе произвольное зануление. Веса скачивать заранее, зафиксировать revision/checksum, инференс сделать локальным. Не менять рабочее окружение защиты: отдельный venv, закреплённые зависимости.

## 4. Следующие кандидаты и ограничения

**TimesFM 2.5** — второй pretrained кандидат, сначала zero-shot. Для будущих календарных ковариат у 2.5 есть XReg; оценивать его отдельно от базовой модели. Официальный репозиторий: https://github.com/google-research/timesfm . На дату исследования уже есть TimesFM 3, но self-hosted веса версии 3 имеют отдельные ограничения non-commercial/non-production; до подтверждения применимости к кейсу не включать их в production-пакет. Версия 2.5 имеет Apache-2.0 веса. Облачный сервис во время инференса несовместим с автономным API-заданием.

**NBEATSx** — кандидат из NeuralForecast для обучения на наших данных с известными будущими признаками; сравнить с TFT при сопоставимом бюджете настройки и той же истории. Приоритет после первого pretrained baseline, а не одновременный большой перебор. Официальный репозиторий: https://github.com/Nixtla/neuralforecast ; статья: https://arxiv.org/abs/2104.05522 . Проверить поддержку необходимых exog именно установленной версией.

**Распределительная модель для редкого спроса** — отдельный эксперт, например DeepAR с подходящей count-distribution при неотрицательном целочисленном таргете. Проверить поддержку нужного распределения в выбранной библиотеке. Сравнивать прогноз средней величины и выбранного на окнах настройки квантиля: их оптимальность для RMSE и SMAPE различается. Если target не целочисленный, не округлять обучающий факт ради выбранной likelihood.

Не забывать дешёвый специализированный контроль для прерывистого спроса (TSB/Croston/SBA) и простую модель тренда. Они нужны для проверки полезности разнообразия, а не ради количества моделей. Регион/режим эксперта выбирать по признакам, известным до cutoff; не по фактическому будущему спросу.

NHITS и TiDE уже запускались в `experiments/benchmarks/`. Средний postprocessed score на старых трёх окнах: NHITS примерно 0.76125, TiDE примерно 0.75470 против TFT примерно 0.73948 на тех же окнах. Перед повтором проверить конфигурации и бюджет: это не доказательство принципиальной слабости архитектур, но повторять тот же эксперимент бессмысленно. Новые результаты пяти окон не сравнивать напрямую со старыми тремя.

## 5. Протокол выбора — обязательный для каждого кандидата

- Одинаковые ключи, weekly target, горизонт 9 недель, доступная до cutoff история. В основном финальном обучении cutoff 2026-07-26, даже если в сыром файле есть данные по 2026-07-31.
- Одинаковая реализация метрик и baseline-нормировки. Локальный score относительно mean13 не равен min-max score лидерборда.
- Все пять текущих окон уже использовались. Не называть их новыми независимыми holdout. Для нового этапа заранее закрепить окна выбора/проверки, либо добавить ещё не использованные допустимые ранние origins; явно учитывать укороченную историю на них. Не подбирать по итоговому окну и потом выдавать его за независимую проверку.
- Малый заранее заданный набор весов/порогов. Для обучаемого stacking/residual-corrector — внутренние временные OOF внутри обучающего периода каждого внешнего окна. Нельзя учить корректор на ошибках того же окна, на котором сообщается выигрыш.
- Сохранить raw, postprocessed и blended прогнозы по ключам, конфигурации, runtime и peak memory. Одинаковая логика во временной проверке и финальном predict.
- Сравнивать каждую модель отдельно с TFT и отдельно её добавление к фиксированному ансамблю. Более слабая одиночная модель может улучшить смесь; низкая корреляция без улучшения метрик не является успехом.
- Для финалистов повторить на нескольких seed, если обучение стохастическое. Не повторять полностью детерминированный zero-shot ради искусственной статистики.
