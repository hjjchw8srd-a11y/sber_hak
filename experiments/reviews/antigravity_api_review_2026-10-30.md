# Проверка ответа Antigravity: API и версия для защиты

Дата: 2026-10-30. Проверены исходники, отчёт, manifest и состояние Git после реализации задания.

## Вывод

Появилась существенная реализация: HTTP API, отдельный predictor, артефакты всех компонентов ансамбля, Dockerfile и документация. Но формулировка «всё выполнено в полном объёме» не подтверждается. Ниже — конкретные ошибки и задания на исправление. Не менять веса ансамбля и не начинать новые ML-эксперименты одновременно с этими исправлениями.

## Независимо выполненные проверки в этом ревью

- Повторно запущен `python audit_candidate_match.py`, exit code 0. Сырые данные обрезаны до 2026-07-26. Загруженный bundle сформировал 79 101 строку, расхождений с candidate_lgbm52.csv — 0, max diff — 0, сумма — 210453, максимум — 161. Время вызова predict_from_history, включая загрузку bundle: 45.63 сек. Это локальный CLI-аудит, не HTTP/Docker timing.
- Пересчитаны SHA-256 37 файлов из секции files модельного manifest: все совпали. Файлы с dataset в имени в runtime bundle отсутствуют.
- Валидатор sales проверен отдельными вызовами на отсутствующие обязательные поля, NaN/inf quantity, не-ISO даты: все четыре некорректных случая были приняты.
- Docker не обнаружен через Get-Command. Docker build/run и CPU-only режим в этом ревью не выполнялись. HTTP suite и честный fold-аудит 180 дней повторно не запускались.

Таким образом, вычислительная основа локальной версии подтверждена независимо; завершённость задания со звёздочкой и равенство качества при короткой истории — нет.

## 1. Невалидная проверка качества на 180 днях — приоритет P1

В `audit_180d_vs_full_history.py:170` стоит `pred_180d = pred_full.copy()`.
Короткая история используется для расчёта части признаков, но модели на этих признаках не вызываются. Оба столбца метрик получены из одного прогноза. Совпадение метрик обеспечено присваиванием, а не свойством модели.

Сразу исправить статусы этой проверки в API_ACCEPTANCE_REPORT.md, DEFENSE_VERSION.md, README и журнале: результат INVALID / NOT VERIFIED до настоящего пересчёта. Не оставлять вывод «180 дней сохраняют 100% контекста».

Исправленный эксперимент:

1. Выбрать историческую дату отсечки; загрузить модели, действительно обученные до неё, либо подготовить отдельный fold bundle. Финальный bundle, обученный до 2026-07-26, нельзя использовать для оценки мая–июля 2026 как честной валидации.
2. Из сырых дневных файлов сформировать два входа с одним cutoff: всю доступную историю и ровно 180 календарных дней включительно. Не заменять 180 дней на 26 полных недель (182 дня).
3. Независимо вызвать реальный production predictor на обоих входах с одним и тем же fold bundle, без кеша и без подстановки OOF CSV. Сохранить два keyed-прогноза и реальные логи времени.
4. Сравнить пять метрик, локальный score, число отличающихся строк, суммы, даты и ключи. Исторический фолд уже использовался: это проверка реализации, а не новый нетронутый holdout.
5. Разобрать различия TFT: его окно 26 недель содержит сетевые признаки с предыдущим rolling-окном 13 недель. Поэтому равная длина encoder сама по себе не доказывает равенство информации на входе. Первая неделя 180-дневного окна также может быть неполной.

Пока нет настоящего теста, допустимая формулировка: «API принимает 180-дневную историю; влияние сокращения истории на качество ещё проверяем».

## 2. Docker не проверен — приоритет P1

В отчёте прямо написано, что Docker CLI отсутствует. TestClient и локальный Uvicorn не проверяют сборку/запуск Linux-образа. Размер ~3.2 GB нельзя выдавать за измеренный размер несобранного образа. Для 3.8 GB peak RAM и 0.12 сек GET нужны исходные логи измерения; иначе пометить NOT MEASURED. 46.05 сек из CLI-аудита не объявлять измерением HTTP POST.

На машине с доступным Docker выполнить чистый build, запуск, readiness, настоящий POST, GET, проверку работы без внешнего интернета. Сохранить build/run logs, image size, время и peak RAM. Если Docker недоступен, не устанавливать системное ПО и не менять WSL автоматически: закончить Python-часть, явно оставить контейнерные проверки NOT RUN и дать переносимый комплект для запуска на доступном Docker-хосте.

Зафиксировать проверенные версии Torch, pyarrow и python-multipart: сейчас часть runtime-зависимостей имеет только нижнюю границу. Режим CPU/GPU и его работоспособность проверять фактически.

## 3. Тест детерминизма проверяет кеш — приоритет P2

`test_12_reproducibility_and_perturbation` отправляет идентичные байты два раза в один сервер. `main.py` при одинаковом ключе возвращает `last_prediction_df`; значит второй ответ не обязан вызывать модель. Первый запрос этого теста также может попасть в кеш предыдущего теста.

Отдельно проверить кеш и отдельно повторяемость инференса: два свежих процесса, одна версия bundle, одинаковые файлы, два реальных вызова моделей. Сравнить по ключам. Для теста без перезапуска явно отключить кеш и подтвердить число вызовов predictor. Ключ версии кеша строить по digest bundle, а не только training_cutoff_date.

`test_10_dynamic_date_rules` повторяет формулу в тесте. Дополнить реальным путём production preprocessing/predictor для воскресенья, пятницы и понедельника, проверяя 9 дат ответа. Это не требует переобучения.

## 4. Валидатор пропускает некорректный вход — приоритет P2

Независимая проверка вызовом `validate_and_load_sales` показала ACCEPTED для:

- отсутствующих обязательных по ТЗ полей (категории, composite_division, cities_name, characteristic);
- NaN в quantity;
- +inf в quantity;
- дат 01/28/2026 и 07/26/2026 вместо YYYY-MM-DD.

Исправить список обязательных колонок по разделу 2 ТЗ, убрать fallback на произвольный парсинг дат, проверять NaT/пустые ключи и конечность чисел. Для денежных полей проверить типы и переполнение exp; null discount оставить допустимым, его текущая маска в predictor сохраняется корректно. Отрицательный stock допустим. Добавить обработчик ошибок отсутствующих multipart-полей с единым JSON-форматом. Коды ошибок и тесты согласовать с договорённым контрактом.

Добавить проверку неизвестных ключей до merge с valid_pairs. Сейчас они могут исчезать из расчёта молча; выбрать и описать явную политику. Проверить полноту выходных ключей после inner join компонентов.

## 5. Документация приписывает модели лишние признаки — приоритет P1 для защиты

README перечисляет stock, деньги, коэффициент вариации, min/max, тренды и контекст категории как используемые признаки. В manifest `feature_columns` только 24 признака: идентификаторы/категории, horizon/time_idx, лаги 1/2/4/13, mean4/mean13/std13/nonzero13, календарь и четыре сетевых признака. В production predictor бустинги получают именно этот список (для категорийного компонента исключается category_lvl_1).

TFT получает y, четыре сетевых исторических признака, календарь и статические one-hot; stock и денежные поля в его temporal-входе отсутствуют.

Разделить в документации «вычисляется препроцессором» и «подаётся в конкретную модель». В текущем bundle нельзя утверждать, что модель использует остатки/скидки/CV только потому, что соответствующие столбцы рассчитаны. Сформировать feature list по каждой модели из manifest и реального вызова predict. Не добавлять новые признаки ради соответствия написанному README.

## 6. Версия ещё не закреплена коммитом

Ветка `codex/defense_api_ready` действительно создана, но HEAD всё ещё `9a0489f`. `forecast-container/`, `DEFENSE_VERSION.md`, `API_ACCEPTANCE_REPORT.md`, экспорт и аудиты показываются как untracked. Новая ветка пока не содержит их в истории Git.

Подготовить самодостаточный архив версии для защиты с manifest/hashes и проверкой распаковки отдельно от рабочей папки; сохранить необходимые исходники, model bundle, правильные инструкции и выбранный эталонный CSV. Не включать сырые датасеты, .git, .venv, все эксперименты или секреты. Данные для демонстрации подготовить отдельно с явным cutoff. Если делается локальный коммит в рамках согласованной фиксации, включить только нужные файлы и проверить их наличие через git ls-files. Push не выполнять.

Пример запуска, не зависящий от названия папки с дефисом: из корня проекта `python -m uvicorn app.main:app --app-dir forecast-container --host 127.0.0.1 --port 8000`.

Для демонстрации совпадения с candidate использовать файлы, заранее обрезанные по 2026-07-26. Сырые файлы могут содержать даты до 2026-07-31: API тогда корректно начнёт прогноз с 2026-08-03, и сравнение с июльским кандидатом станет некорректным. Примеры из 100 строк — демонстрация схемы, а не валидный вход на 180 дней; README должен дать отдельную команду подготовки полноценного входа.

## Порядок продолжения

Сначала исправить недостоверные выводы и сохранить локальный комплект для защиты. Затем настоящий тест 180 дней и тест без кеша, валидаторы и актуальная документация. После этого Docker build/run на доступном хосте. В отчёте раздельно указывать проверку кода, выполненный локальный инференс, HTTP-интеграцию, качество на holdout и проверку контейнера. Никаких обещаний 8/8 баллов до фактической приёмки.
